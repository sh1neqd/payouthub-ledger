# Модель Ledger

Ledger хранит деньги мерчантов внутри PayoutHub, резервирует их под выплаты
и сохраняет историю движения. Payments управляет выплатой, а Processing
получает результат от эмулятора провайдера. Ledger отвечает за то, чтобы
повторный запрос не изменил деньги повторно и незавершённая операция
не оставила половину изменений в базе.

Первая версия поддерживает RUB, полное списание или освобождение резерва
и один счёт мерчанта на валюту. Частичные списания, комиссии, конвертация
и автоматическое освобождение по времени в эту версию не входят.

## Что уже есть в проекте

`Account` содержит `Id`, `Balance`, `Reserved`. Метод `Available` считает
доступную сумму, а `Reserve` проверяет сумму и меняет объект в памяти.
PostgreSQL пока хранит только `accounts`; репозиторий умеет создавать
и читать счёт.

Эта модель определяет дальнейшую реализацию. Наличие метода `Reserve`
в Go ещё не означает, что резерв сохранён в PostgreSQL или защищён
от одновременных запросов.

## Денежные суммы

Во всех запросах, объектах Go и таблицах суммы выражаются в копейках.
1 000 рублей — это `100000`. Для сумм используем Go `int64` и PostgreSQL
`BIGINT`. Дробных чисел и конвертации валют в первой версии нет.

Сумма FundAccount и Reserve должна быть положительной. Capture и Release
берут сумму из сохранённого hold: клиент не передаёт сумму заново.
Перед сложением и вычитанием проверяем, что результат помещается в `int64`.
Переполнение не должно превращать большой положительный остаток в отрицательный.

У счёта мерчанта три связанные величины:

| Величина | Значение |
| --- | --- |
| `balance` | Деньги, которые ещё находятся на счёте |
| `reserved` | Часть этих денег, занятая активными выплатами |
| `available` | Деньги, доступные для новой выплаты: `balance - reserved` |

Например, при `balance = 100000` и `reserved = 30000` деньги на 300 рублей
ещё не списаны. Но использовать их для второй выплаты уже нельзя.

Для wallet всегда выполняется:

```text
balance >= 0
reserved >= 0
reserved <= balance
available = balance - reserved
```

`available` не храним отдельным столбцом. Иначе пришлось бы обновлять
три связанных значения и следить, чтобы они не разошлись.

## Счета

Выбираем три типа счетов:

| Тип | Назначение | Остаток | Резерв |
| --- | --- | --- | --- |
| `wallet` | Деньги конкретного мерчанта | Неотрицательный | От 0 до balance |
| `funding` | Парная сторона учебного пополнения | Может быть отрицательным | Всегда 0 |
| `settlement` | Парная сторона завершённой выплаты | Неотрицательный | Всегда 0 |

Технические счета нужны для парных записей движения денег. Их остатки
показывают, сколько в учебной модели зачислили и выплатили. Они не являются
подтверждением реального остатка на банковском счёте.

В первой версии создаём по одному техническому счёту каждого типа для RUB.
Они создаются при подготовке окружения. Обычный CreateAccount открывает
только wallet с нулевыми остатками.

Поля `accounts`:

| Поле | Тип | Правило |
| --- | --- | --- |
| `id` | BIGINT identity | Положительный ID, сохраняем текущий подход |
| `kind` | Текст | wallet, funding или settlement |
| `merchant_id` | UUID или NULL | Обязателен для wallet, отсутствует у технических счетов |
| `currency` | Текст | Только RUB, после открытия не меняется |
| `balance` | BIGINT | Текущий остаток, изначально 0 |
| `reserved` | BIGINT | Общая сумма активных hold, изначально 0 |
| `created_at` | TIMESTAMPTZ | Время открытия |

Тип и владелец счёта после открытия не меняются. Для wallet уникальна пара
`merchant_id, currency`. Для технических счетов уникальна пара `kind, currency`.
При повторном CreateAccount для того же мерчанта и валюты возвращаем
существующий wallet. Деньги при этом не меняются.

В текущей миграции отрицательный balance запрещён для всех счетов. В PH-03
новой миграцией заменим это ограничение на проверку с учётом типа счёта.
Ограничение `reserved <= balance` также применяем только к wallet:
у funding возможны `balance < 0` и `reserved = 0`.
Уже применённый файл миграции не переписываем.

Общие технические счета означают, что завершения выплат могут ждать блокировку
одной и той же строки. Для первой версии это приемлемо. На PH-17 проверим,
становится ли это ограничением под нагрузкой.

## История движения денег

Проводка — запись изменения денег на одном счёте. Например, `+100000`
означает зачисление 1 000 рублей, а `-30000` — списание 300 рублей.

Одна журнальная транзакция объединяет проводки одного движения.
В первой версии их ровно две, валюта одна, а сумма изменений равна нулю.
Это выбранная модель нашего проекта; знаки обозначают изменение остатка.

Пополнение на 1 000 рублей:

```text
funding: -100000
wallet:  +100000
сумма:        0
```

Завершённая выплата на 300 рублей:

```text
wallet:     -30000
settlement: +30000
сумма:          0
```

### Журнальная транзакция

`journal_transactions` хранит заголовок движения:

| Поле | Тип | Правило |
| --- | --- | --- |
| `id` | UUID | Ledger создаёт ID нового движения |
| `operation_id` | UUID | Операция, которая впервые создала это движение; уникальная связь |
| `kind` | Текст | fund или capture |
| `currency` | Текст | RUB |
| `hold_id` | UUID или NULL | Для capture обязателен, для fund отсутствует |
| `created_at` | TIMESTAMPTZ | Время записи |

Для одного hold допускается одна журнальная транзакция capture.
Это дополнительно ограничиваем уникальностью `hold_id` для записей capture.

### Проводка

`journal_entries` хранит строки движения:

| Поле | Тип | Правило |
| --- | --- | --- |
| `id` | BIGINT identity | ID строки журнала |
| `transaction_id` | UUID | Ссылка на journal_transactions |
| `account_id` | BIGINT | Ссылка на accounts |
| `delta` | BIGINT | Изменение остатка со знаком; не равно 0 |

Валюта задаётся в заголовке и должна совпадать с валютой обоих счетов.
Поля `transaction_id` и `account_id` защищаем внешними ключами.

`accounts.balance` хранится для быстрых проверок, но должен совпадать
с суммой всех проводок этого счёта. Обновление остатков и запись журнала
происходят в одной транзакции PostgreSQL.

Перед фиксацией проверяем состав проводок, их валюту и нулевую сумму.
Обычный CHECK одной строки не может заменить проверку двух строк движения.
В первой версии запись идёт только через приложение Ledger.

Проведённые записи не исправляем через UPDATE и не удаляем через API.
Корректировка в дальнейшем будет отдельным обратным движением со ссылкой
на исходное; публичный метод корректировки сейчас не реализуем.

## Резерв

`reserved` показывает общую занятую сумму. Отдельный `hold` объясняет,
какая выплата заняла конкретную часть денег.

Если зарезервировали 300 и 200 рублей для разных выплат, на счёте
`reserved = 50000`, а в таблице holds лежат две активные записи.
Одного поля reserved недостаточно, чтобы безопасно завершить каждую выплату.

Поля `holds`:

| Поле | Тип | Правило |
| --- | --- | --- |
| `id` | UUID | Ledger создаёт при первом успешном Reserve |
| `payout_id` | UUID | ID выплаты из Payments; уникален в Ledger |
| `account_id` | BIGINT | Wallet, на котором держим деньги |
| `amount` | BIGINT | Положительная сумма в копейках |
| `currency` | Текст | RUB, совпадает с валютой wallet |
| `status` | Текст | active, captured или released |
| `reserve_operation_id` | UUID | Операция, впервые создавшая hold |
| `capture_operation_id` | UUID или NULL | Первое успешное списание этого hold |
| `release_operation_id` | UUID или NULL | Первое успешное освобождение этого hold |
| `created_at` | TIMESTAMPTZ | Время создания |
| `completed_at` | TIMESTAMPTZ или NULL | Время конечного перехода |

Счёт, выплата, сумма и валюта hold после создания неизменны.
Ссылки на счёт и операции защищаем внешними ключами.
Активный hold не имеет completed_at и конечных operation ID.
У captured заполнен только capture_operation_id, у released — только
release_operation_id. Оба конечных поля одновременно заполнены быть не могут.

```text
active → captured
active → released
```

Конечное состояние не возвращается в active. Для повторной бизнес-попытки
после завершения Payments создаёт новую выплату с новым payout_id.

Резерв не освобождается автоматически по таймеру. Если ответ провайдера
потерялся, он мог уже выполнить выплату. До выяснения результата деньги
остаются зарезервированными.

## Операция и повторные запросы

Словом «транзакция» часто называют разные вещи. В этом проекте различаем:

| Понятие | Что означает |
| --- | --- |
| Operation | Запрос клиента выполнить действие и сохранённый результат |
| JournalTransaction | Движение денег с парой проводок |
| Транзакция PostgreSQL | Группа изменений БД, которая сохраняется целиком или откатывается |

Reserve создаёт Operation и Hold, но не создаёт JournalTransaction:
деньги ещё находятся на wallet.

Поля `operations`:

| Поле | Тип | Правило |
| --- | --- | --- |
| `id` | UUID | operation_id, присланный клиентом; глобально уникален в Ledger |
| `kind` | Текст | fund, reserve, capture или release |
| `request` | JSONB | Нормализованные значимые параметры запроса |
| `request_hash` | BYTEA | SHA-256 канонического представления kind и параметров |
| `status` | Текст | processing внутри незавершённой транзакции; succeeded или rejected после фиксации |
| `result` | JSONB или NULL | Сохранённый успешный результат с версией формата |
| `error_code` | Текст или NULL | Сохранённая причина бизнес-отказа |
| `created_at` | TIMESTAMPTZ | Время начала |
| `completed_at` | TIMESTAMPTZ или NULL | Время завершения |

Payments создаёт operation_id до первого вызова и сохраняет его у себя.
Reserve, Capture и Release одной выплаты имеют разные operation_id.
При повторе конкретного действия используется его прежний ID.

Например, выплата P1 имеет три разных идентификатора: ID самой выплаты,
ID команды Reserve и ID созданного резерва. Capture получает ID резерва
и собственный ID команды. Нельзя использовать один operation_id
сначала для Reserve, а потом для Capture.

Сравниваем смысл запроса, а не байты произвольного JSON. Порядок JSON-полей
не должен превращать повтор в конфликт. Нормализация использует известные
поля конкретного метода, канонические UUID и RUB. Формат отпечатка фиксируем
как v1 и не меняем для уже сохранённых операций.

Трассировочные данные и сетевой deadline в отпечаток не входят.
Для Capture и Release значимый параметр — hold_id; сумму берём из hold.

### Поведение при повторе ID

| Ситуация | Ответ | Изменение денег |
| --- | --- | --- |
| Новый ID, корректный запрос | Выполнить и сохранить результат | По правилам метода |
| Прежний ID, те же параметры | Вернуть сохранённый результат | Нет |
| Прежний ID, другие параметры или метод | IDEMPOTENCY_CONFLICT | Нет; исходную запись не менять |
| Два одновременных запроса с одним ID | Один выполняет; второй ждёт в пределах deadline и затем читает результат | Один раз |

Сначала находим существующую операцию и проверяем отпечаток. Только для
новой операции проверяем текущий остаток и меняем деньги. Иначе повтор
успешного Reserve мог бы ошибочно получить отказ из-за уже занятой суммы.

Промежуточное processing существует лишь внутри открытой транзакции БД.
Ledger не фиксирует его отдельным commit и не создаёт фонового задания
для денежной операции. Commit допустим после установки succeeded
или rejected. При падении процесса до commit откатывается и эта запись.

### Успешный ответ

Сохраняем версию формата, effective_operation_id, ID счёта, сумму, валюту,
остатки после операции и, если применимо, ID hold, его состояние после
действия и ID журнальной транзакции. Это снимок результата действия.

Повтор возвращает этот снимок. Если после Reserve прошёл Capture,
старый результат Reserve не переписывается. Текущие остатки и состояние
получаем отдельными GetAccount и GetHold.

### Бизнес-отказ и технический сбой

Если сумма корректна, ID принят, но денег недостаточно, сохраняем
`rejected` с `INSUFFICIENT_FUNDS`. Денежных изменений и нового hold нет.
После пополнения повтор этого ID всё равно возвращает прежний отказ.
Новая попытка резервирования получает новый operation_id; payout_id
может остаться прежним, если hold для него ещё не был создан.

По той же политике сохраняем ошибки ACCOUNT_NOT_FOUND, HOLD_NOT_FOUND,
INVALID_ACCOUNT_KIND, CURRENCY_MISMATCH, AMOUNT_OVERFLOW,
HOLD_STATE_CONFLICT и PAYOUT_CONFLICT. Они описывают результат принятой
команды, а не состояние сети.

Некорректный UUID, неположительная входная сумма, отсутствующее обязательное
поле или неизвестная валюта отклоняются при проверке формата запроса.
Такая команда не создаёт запись operations.

При потере соединения, deadlock или откате транзакции не фиксируем
технический сбой как окончательный бизнес-отказ. Повторяем всю операцию
с тем же ID. Если ответ на commit потерялся, сначала считаем результат
неизвестным: commit мог состояться. Повтор с прежним ID или GetOperation
позволяет выяснить итог.

Отсутствие записи в GetOperation не является доказательством, что вызов
не выполняется прямо сейчас: его транзакция ещё может быть открыта.
Безопасный следующий запрос использует прежний operation_id.

Срок ожидания ответа ограничивает клиента, но сам по себе не является
доказательством отката денежной операции. У gRPC есть deadline и отмена
вызова; приложение должно учитывать отмену в своей работе.
[Документация gRPC о deadline](https://grpc.io/docs/guides/deadlines/)

## Контракты действий

Ниже — смысл будущих методов. Protobuf и обработчики появятся в PH-07.

| Метод | Вход | Результат |
| --- | --- | --- |
| CreateAccount | merchant_id, currency | Новый нулевой wallet или существующий wallet этой пары |
| GetAccount | account_id | Текущий kind, merchant_id, currency, balance, reserved, available |
| FundAccount | operation_id, account_id, amount, currency | Сохранённый результат пополнения и ID движения |
| Reserve | operation_id, payout_id, account_id, amount, currency | Сохранённый результат и hold_id |
| Capture | operation_id, hold_id | Сохранённый результат полного списания и ID движения |
| Release | operation_id, hold_id | Сохранённый результат освобождения |
| GetHold | hold_id | Текущие параметры и состояние hold |
| GetOperation | operation_id | Сохранённый успех или бизнес-отказ; отсутствие записи отдельно |
| ListEntries | account_id, after_entry_id, limit | Проводки счёта по возрастанию ID, limit от 1 до 100 |

Клиент не выбирает технический счёт для пополнения или списания — его
определяет Ledger по типу действия и валюте. FundAccount предназначен
для управляемого учебного пополнения. Payments не предоставляет пользователю
публичную возможность произвольно увеличить balance.

Проверка владельца выплаты находится в Payments. Ledger сохраняет владельца
wallet, доступен только доверенным внутренним клиентам и не принимает
выплату с чужим account_id через публичный интерфейс. Сетевая настройка
доступа и аутентификация не заменяются одним полем merchant_id.

### FundAccount

После проверки повтора блокируем funding и wallet. Проверяем тип wallet,
совпадение валюты и отсутствие переполнения обоих остатков.

В одной транзакции PostgreSQL:

1. Уменьшаем balance funding на amount.
2. Увеличиваем balance wallet на amount; reserved не меняется.
3. Создаём JournalTransaction fund и две соответствующие проводки.
4. Сохраняем успешный результат Operation.

### Reserve

После проверки повтора блокируем wallet и проверяем, существует ли hold
для payout_id. Эта проверка предшествует проверке достаточности средств
для нового резерва.

Если hold уже есть и его счёт, сумма и валюта совпадают, возвращаем снимок
первого успешного Reserve и сохраняем результат новой команды без изменений
денег. effective_operation_id указывает на первоначальный Reserve.
Если параметры отличаются, сохраняем PAYOUT_CONFLICT.

Если hold отсутствует, проверяем `amount <= available`. В одной транзакции
создаём активный hold, увеличиваем reserved и сохраняем результат операции.
Balance и журнал не меняются.

Уникальность payout_id защищает и от одновременных запросов с разными
operation_id. Если другой запрос успел создать hold, сравниваем параметры
с его записью и применяем правило выше. Нельзя сначала увеличить reserved,
а потом оставить это увеличение после конфликта создания hold.

Повтор Reserve для уже завершённого payout_id не открывает hold заново.
При совпадении параметров возвращается результат первого Reserve;
текущее состояние определяется через GetHold.

### Capture

Сначала получаем неизменяемый account_id из hold. Блокируем wallet
и settlement, затем hold и повторно читаем его состояние.

Для active перед изменениями проверяем, что увеличение settlement.balance
помещается в int64. При AMOUNT_OVERFLOW hold остаётся active.

В одной транзакции:

1. Уменьшаем wallet.balance и wallet.reserved на hold.amount.
2. Увеличиваем settlement.balance на hold.amount.
3. Создаём JournalTransaction capture и две проводки.
4. Переводим hold в captured и записываем время и capture_operation_id.
5. Сохраняем успешный результат Operation.

Для captured возвращаем первоначальный успешный Capture. Даже при новом
operation_id второго списания и новой журнальной транзакции нет; новая
Operation сохраняет тот же результат с исходным effective_operation_id.
Для released возвращаем HOLD_STATE_CONFLICT.

Capture не пересчитывает достаточность свободных денег: сумма уже занята
этим hold. Проверяем связь hold со счётом, состояние, reserved и balance.
Если активный hold не покрывается сохранёнными остатками, это нарушение
учёта. Откатываем транзакцию, сообщаем техническую ошибку и не пытаемся
«исправить» остатки в обработчике.

### Release

Блокируем wallet, затем hold и проверяем актуальное состояние.
Для active дополнительно проверяем, что reserved покрывает hold.amount.
Расхождение означает нарушение учёта: откатываем действие с технической ошибкой.

Для active в одной транзакции уменьшаем reserved на hold.amount,
переводим hold в released, записываем время и release_operation_id
и сохраняем успешный результат Operation. Balance и журнал не меняются.

Для released возвращаем первоначальный успешный Release без повторного
уменьшения reserved. Новый operation_id сохраняется с тем же результатом
и исходным effective_operation_id. Для captured возвращаем HOLD_STATE_CONFLICT.

## Одновременные операции

Для первой версии используем READ COMMITTED и явные блокировки строк.
`SELECT ... FOR UPDATE` удерживает блокировку до конца транзакции;
другие изменяющие эту строку транзакции ждут. Обычное чтение счёта
не становится заблокированным только из-за FOR UPDATE.
[Блокировки PostgreSQL](https://www.postgresql.org/docs/current/explicit-locking.html)

Два запроса с одним operation_id сериализуются уникальным ключом operations.
Захват ID и сохранение конечного результата выполняются в одной транзакции.
Если вставка не состоялась из-за конкурирующего запроса, следующим чтением
получаем зафиксированную запись. Не продолжаем денежную часть команды
как будто ID всё ещё новый. При READ COMMITTED отдельные команды внутри
транзакции могут видеть более свежие зафиксированные данные.
[Изоляция PostgreSQL](https://www.postgresql.org/docs/current/transaction-iso.html)

Общий порядок для изменяющих методов:

1. Захватить или проверить operation_id.
2. Определить все затрагиваемые счета по неизменяемым параметрам.
3. Заблокировать счета по возрастанию account_id.
4. Если нужен существующий hold, заблокировать его после счетов.
5. Проверить актуальные условия, изменить данные, сохранить результат и сделать commit.

Этот порядок одинаков для FundAccount, Reserve, Capture и Release.
Capture и Release не должны начинать с блокировки hold, а затем ждать
wallet, пока Reserve использует обратный порядок.

READ COMMITTED сам по себе не гарантирует достаточность денег: защиту
даёт проверка актуального остатка под блокировкой. Все пути изменения
счёта должны соблюдать один протокол.

Если два Reserve по 700 рублей приходят при balance 1 000 рублей,
первый успешный commit оставляет available 300 рублей. Второй после
ожидания читает этот остаток и получает INSUFFICIENT_FUNDS.

Если Capture и Release одного hold приходят одновременно, побеждает
первый успешно зафиксированный переход. Если его транзакция откатилась,
второй может выполнить переход. Мы не выбираем победителя по времени
отправки запроса или запуска goroutine.

Внутри денежной транзакции нет сетевых вызовов в Payments, Processing,
Kafka или провайдера. Все изменения здесь локальны для PostgreSQL Ledger.
Отказанное бизнес-действие сохраняет только rejected Operation;
частичные денежные изменения до фиксации отказа откатываются.

## Пример полного цикла

В этом разделе суммы наглядно показаны в рублях. В коде и БД каждую
сумму умножаем на 100. Обозначения F1, R1, C1 и L1 заменяют длинные UUID.

### Начальное состояние

```text
wallet W1: balance 0, reserved 0, available 0
funding: balance 0
settlement: balance 0
```

### Пополнение F1 на 1 000 рублей

Создаём Operation F1, JournalTransaction J1 и проводки funding -1000,
wallet +1000. В той же транзакции меняем остатки.

```text
W1: balance 1000, reserved 0, available 1000
funding: -1000
settlement: 0
```

### Reserve R1 на 300 рублей для выплаты P1

Создаём Hold H1 со статусом active и amount 300. Создаём успешную
Operation R1. У wallet увеличиваем только reserved.

```text
W1: balance 1000, reserved 300, available 700
H1: active
funding: -1000
settlement: 0
```

Журнал по-прежнему содержит только J1. Сумма проводок wallet равна 1000.
Это соответствует balance, а не available.

### Успешная выплата и Capture C1

Payments получает подтверждённый успех провайдера и вызывает Capture H1.
Создаём Operation C1, JournalTransaction J2 и проводки wallet -300,
settlement +300. Одновременно завершаем hold и уменьшаем оба поля wallet.

```text
W1: balance 700, reserved 0, available 700
H1: captured
funding: -1000
settlement: 300
```

Журнал wallet объясняет balance: `1000 - 300 = 700`. Общая сумма остатков
трёх счетов: `-1000 + 700 + 300 = 0`.

### Альтернативный отказ и Release L1

Эта ветка начинается после Reserve, вместо Capture. После подтверждённого
отказа провайдера Payments вызывает Release H1.

```text
W1: balance 1000, reserved 0, available 1000
H1: released
funding: -1000
settlement: 0
```

Новых проводок нет. Деньги не уходили со счёта, поэтому возвращать их
пополнением не нужно. Нужно лишь сделать снова доступными те 300 рублей,
которые раньше были заняты выплатой.

## Проверочные сценарии

| Сценарий | Ожидаемый результат |
| --- | --- |
| Повтор FundAccount F1 | Текущий остаток не меняется, новые проводки не появляются; возвращается первоначальный результат F1 |
| Повтор F1 с суммой 2000 | IDEMPOTENCY_CONFLICT, прежние остатки |
| Повтор Reserve R1 | Тот же H1, reserved не растёт повторно |
| Новый Reserve с другим ID, но тем же P1 и параметрами | Тот же H1 и первый результат Reserve |
| Reserve с тем же P1 и другой суммой или счётом | PAYOUT_CONFLICT |
| Reserve на 1200 при balance 1000 | Rejected Operation, hold не создан, деньги не меняются |
| Пополнение после отказа и повтор отказанного ID | Прежний INSUFFICIENT_FUNDS |
| Новый ID команды после пополнения | Новая проверка денег; прежний payout_id допустим, если hold ещё отсутствует |
| Capture H1 два раза | Одна J2, wallet списан один раз |
| Release H1 два раза | reserved уменьшен один раз, новых проводок нет |
| Capture после Release | HOLD_STATE_CONFLICT |
| Release после Capture | HOLD_STATE_CONFLICT |
| Два Reserve по 700 при balance 1000 | Один успех, один отказ; reserved 700 |
| Capture и Release H1 одновременно | Один конечный переход, второму конфликт |
| Процесс упал до commit Capture | Нет частично сохранённых денег, журнала или конечного состояния hold |
| Commit Capture прошёл, но ответ потерялся | Повтор находит сохранённый успех без нового списания |
| GetOperation не нашёл запись, исходный вызов ещё работает | Повтор прежнего ID; отсутствие записи не разрешает новое списание с новым ID |
| Ответ провайдера не определён | Hold остаётся active; Release по таймеру запрещён |

## Сверка учёта

В согласованном снимке БД проверяем:

```text
Для каждого счёта:
accounts.balance = сумма journal_entries.delta этого счёта

Для каждого wallet:
accounts.reserved = сумма holds.amount, где status = active

Для каждой журнальной транзакции:
ровно две проводки одной валюты, сумма delta = 0

Для каждого captured hold:
ровно одна соответствующая журнальная транзакция capture

Для каждой зафиксированной операции:
конечный статус succeeded или rejected, completed_at заполнен;
у succeeded есть result, у rejected есть error_code
```

Начальные остатки равны нулю, поэтому отдельная величина начального
balance в формуле не нужна. Несколько запросов сверки должны читать
один согласованный снимок, например в read-only REPEATABLE READ;
иначе commit между запросами может дать ложное расхождение.
Агрегаты считаем без переполнения.

Если в нынешней учебной БД уже есть ненулевые остатки, перед переходом
на журнал нужны контролируемые начальные проводки. Если есть reserved
без hold, сначала выясняем происхождение резерва. Не обнуляем и не
оставляем такие данные без объяснения. Конкретный перенос входит в PH-03.
